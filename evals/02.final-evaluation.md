**Q15.** Ces deux tests testent la même fonctionnalité. Lesquelles de ces affirmations sont **vraies** ? *(plusieurs réponses possibles)*

```typescript
// Test A
it('should transfer money between accounts', () => {
  const source = new Account(100);
  const destination = new Account(50);
  source.transferTo(destination, 30);
  expect(source.balance).toBe(70);
  expect(destination.balance).toBe(80);
});
```

```typescript
// Test B
it('should call debit and credit on transfer', () => {
  const accountRepo = mock<AccountRepository>();
  const useCase = new TransferUseCase(accountRepo);
  when(accountRepo.findById('A')).thenReturn(account(100));
  when(accountRepo.findById('B')).thenReturn(account(50));

  useCase.execute({ from: 'A', to: 'B', amount: 30 });

  verify(accountRepo.save(accountWith({ balance: 70 }))).once();
  verify(accountRepo.save(accountWith({ balance: 80 }))).once();
});
```

- a) Test A part du domaine (Inside-Out) et laisse émerger le design
- b) Test B isole le Use Case de son infrastructure grâce aux mocks
- c) Test A utilise des mocks pour isoler les collaborateurs
- d) Test B est caractéristique de l'école de Londres (Outside-In)
- e) Les deux approches produisent exactement le même design

## Module 5 - Type-Driven Development

**Q17.** Observez ces deux approches. Laquelle applique le principe **"Parse, Don't Validate"** ?

```typescript
// Approche A
function createUser(email: string, age: number): User {
  if (!email.includes('@')) throw new Error('Invalid email');
  if (age < 0 || age > 150) throw new Error('Invalid age');
  return { email, age }; // email et age restent des primitives
}
```

```typescript
// Approche B
class Email {
  private constructor(readonly value: string) {}
  static parse(raw: string): Either<string, Email> {
    if (!raw.includes('@')) return left('Invalid email');
    return right(new Email(raw));
  }
}

class Age {
  private constructor(readonly value: number) {}
  static parse(raw: number): Either<string, Age> {
    if (raw < 0 || raw > 150) return left('Invalid age');
    return right(new Age(raw));
  }
}
```

- a) Approche A - elle valide les données à l'entrée
- b) Approche B - elle transforme les primitives en types qui garantissent leur validité
- c) Les deux approches sont équivalentes
- d) Approche A, car elle lève des exceptions explicites

**Q18.** Pourquoi le constructeur de `EID` est-il **privé** dans ce code ?

```typescript
class EID {
  private constructor(
    readonly sex: Sex,
    readonly year: BirthYear,
    readonly serial: SerialNumber,
    readonly key: ControlKey
  ) {}

  static parse(raw: string): Either<string, EID> {
    return pipe(
      parseSex(raw[0]),
      flatMap(sex => parseBirthYear(raw.slice(1, 3))
        .map(year => ({ sex, year }))),
      flatMap(({ sex, year }) => parseSerialNumber(raw.slice(3, 6))
        .map(serial => ({ sex, year, serial }))),
      flatMap(({ sex, year, serial }) => parseControlKey(raw.slice(6, 8), sex, year, serial)
        .map(key => new EID(sex, year, serial, key)))
    );
  }
}
```

- a) Pour améliorer les performances à l'exécution
- b) Pour empêcher la construction d'un `EID` dans un état invalide en dehors de `parse`
- c) Pour faciliter la sérialisation JSON
- d) Parce que TypeScript l'exige pour les classes avec `Either`

**Q19.** Lesquelles de ces pratiques font partie du **Type-Driven Development** ? *(plusieurs réponses possibles)*

```typescript

type Result<T> = { ok: true; value: T } | { ok: false; error: string };

class SerialNumber {
  private constructor(readonly value: number) {}
```

- e) Écrire des property-based tests pour valider des invariants (ex : `parse(serialize(x)) === x`)
