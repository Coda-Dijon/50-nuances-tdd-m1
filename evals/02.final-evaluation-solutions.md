## Module 2 - TCR

**Q5. ✅ c) Test && Commit || Revert**

TCR est une discipline proposée par Kent Beck : si les tests passent → commit automatique ; sinon → revert automatique. Le `&&` et `||` sont littéralement les opérateurs logiques du script shell.

---

**Q6. ✅ b) Les tests ont échoué et le code a été automatiquement revert**

L'entrée `[REVERT] - tests failed` est générée automatiquement par le script TCR lorsque les tests échouent. Ce n'est pas une action manuelle du développeur : le code est perdu, il doit recommencer à partir du dernier commit vert.

---

**Q7. ✅ a), c) et e)**

- **a) ✅** - `run_tests && git commit` : si les tests passent, le commit est fait automatiquement.
- **b) ❌** - TCR est une discipline complémentaire, pas un remplacement du TDD.
- **c) ✅** - `git checkout .` supprime tous les fichiers modifiés non commités, ramenant au dernier état propre.
- **d) ❌** - Le refactoring reste nécessaire ; TCR s'applique aussi pendant la phase refactor.
- **e) ✅** - La menace du revert encourage naturellement des changements très petits et fréquents.

---

**Q8. Éléments de réponse attendus (2 pts)**

| Critère                                                                               | Points |
|---------------------------------------------------------------------------------------|--------|
| Identifie un avantage (discipline des petits pas, historique propre, sécurité)        | 0,5    |
| Identifie une limite (perte de code, frustration, difficile sur des sujets complexes) | 0,5    |
| Mentionne les deux reverts consécutifs comme signal d'un pas trop grand               | 0,5    |
| Propose un contexte d'usage pertinent (kata, apprentissage, pair programming)         | 0,5    |

**Réponse type :** L'historique montre deux reverts consécutifs (`7d9c0b1` et `6c8b9a0`), signe que les développeurs ont tenté un changement trop ambitieux. **Avantage :** TCR impose une granularité fine et produit un historique git sans bruit - chaque commit est vert par construction. **Limite :** perdre du code sur revert peut être frustrant, et TCR est difficile à appliquer sur des refactorings complexes ou lorsque le cycle de feedback des tests est long. **Contexte idéal :** lors d'un kata d'apprentissage ou en pair programming pour s'entraîner à la discipline des baby steps.

## Module 3 - BDD

**Q9. ✅ d) Given**

`Given` décrit le contexte initial (l'état du système avant l'action). `When` décrit l'action déclenchée. `Then` décrit le résultat attendu.

---

**Q10. ✅ b) `When l'utilisateur soumet le formulaire de connexion`**

`When` introduit l'action de l'utilisateur. Les autres options violent la syntaxe Gherkin : `Then` ne peut pas précéder `When`, et `Given` ne répète pas le contexte après `When`.

## Module 4 - TDD Outside-In

**Q13. ✅ c) Par un test d'acceptation de haut niveau**

L'école de Londres applique le principe Outside-In : on commence par définir le comportement attendu du système depuis l'extérieur (test d'acceptation), puis on descend progressivement vers les unités internes. L'école de Chicago fait l'inverse (Inside-Out).

---

**Q14. ✅ b) Interface B - elle abstrait l'accès à une source de données externe**

`AccountRepository` est un Gateway : elle définit un contrat entre le domaine et l'infrastructure (base de données, API externe, fichier...). L'interface A (`TransferUseCase`) est un Use Case - elle orchestre la logique métier mais n'abstrait pas une ressource externe.

---

**Q15. ✅ a), b) et d)**

- **a) ✅** - Le Test A crée directement des `Account` et teste le comportement via le domaine. Aucun mock, le design émerge du modèle.
- **b) ✅** - Le Test B mock `AccountRepository` pour isoler le `TransferUseCase` de la base de données.
- **c) ❌** - Le Test A n'utilise aucun mock.
- **d) ✅** - Le Test B est typique de l'école de Londres : on teste un Use Case en isolation grâce aux mocks de ses collaborateurs.
- **e) ❌** - Les deux approches peuvent mener à des designs différents. L'école de Londres tend à créer plus d'interfaces et d'indirections.

---

**Q16. Éléments de réponse attendus (2 pts)**

| Critère                                                                                       | Points |
|-----------------------------------------------------------------------------------------------|--------|
| Identifie un contexte où Outside-In est pertinent (architecture hexagonale, infra changeante) | 0,5    |
| S'appuie sur le Test B pour illustrer l'isolation Use Case / infrastructure                   | 0,5    |
| Mentionne une limite ou contrepartie (plus de mocks, plus d'interfaces)                       | 0,5    |
| Comparaison avec Inside-Out ancrée sur les deux tests                                         | 0,5    |

**Réponse type :** L'approche Outside-In (Test B) est préférable lorsque l'architecture hexagonale est en place et que l'on veut isoler la logique métier de son infrastructure dès le départ - par exemple si la source de données peut changer (SQL → NoSQL) ou si l'on travaille en équipe avec des contrats d'interfaces explicites. Le mock de `AccountRepository` permet de tester le `TransferUseCase` sans base de données. En revanche, si le domaine est simple et l'architecture peu stratifiée, l'Inside-Out (Test A) est plus direct et produit moins d'indirections.

## Module 5 - Type-Driven Development

**Q17. ✅ b) Approche B - elle transforme les primitives en types qui garantissent leur validité**

L'approche A *valide* (lève une exception si invalide, mais retourne encore un `string` et un `number` - rien n'empêche de passer une `email` invalide ailleurs dans le système). L'approche B *parse* : après `Email.parse(raw)`, si le résultat est un `Right<Email>`, il est **impossible** de construire un `Email` invalide - le type lui-même le garantit.

---

**Q18. ✅ b) Pour empêcher la construction d'un `EID` dans un état invalide en dehors de `parse`**

Le constructeur privé garantit que la seule façon de créer un `EID` est via `EID.parse()`, qui valide chaque composant avant d'appeler `new EID(...)`. Il est donc **impossible** d'instancier un `EID` avec des champs incorrects - le compilateur le refuse. C'est l'application directe du principe "Make Illegal States Unrepresentable".

---

**Q19. ✅ a), c), d) et e)**

- **a) ✅** - La Pratique X (`Result<T>`) modélise le succès ou l'échec sans exceptions : c'est un pilier du Type-Driven.
- **b) ❌** - La Pratique Y est un exemple de *primitive obsession* - c'est exactement ce que le Type-Driven cherche à éviter.
- **c) ✅** - La Pratique Z encapsule `number` dans `SerialNumber` avec une construction contrôlée via `Either`.
- **d) ✅** - Rendre les états illégaux inreprésentables est le principe central du Type-Driven.
- **e) ✅** - Les property-based tests (ex : round-trip `parse(serialize(x)) === x`) valident les invariants des types.

**Q20. Éléments de réponse attendus (2 pts)**

| Critère                                                                            | Points |
|------------------------------------------------------------------------------------|--------|
| Nomme le problème : primitive obsession / strings interchangeables                 | 0,5    |
| Explique le risque : aucune erreur de compilation si les arguments sont inversés   | 0,5    |
| Propose des types métier (`PassengerId`, `AirportCode`, `FlightDate`, `SeatClass`) | 0,5    |
| La version améliorée rend l'appel incorrect impossible à la compilation            | 0,5    |

**Réponse type :** Le problème est la **primitive obsession** : cinq `string` interchangeables en paramètres. L'appel `bookFlight("PAR", "CDG", "P001", "economy", "2024-12-25")` compile sans erreur même si les arguments sont dans le mauvais ordre. Le Type-Driven y répond en introduisant des types métier :

```typescript
// Après
function bookFlight(
  passengerId: PassengerId,
  departure: AirportCode,
  destination: AirportCode,
  date: FlightDate,
  seatClass: SeatClass
): BookingRef {
  return generateBookingRef(passengerId, departure, destination);
}

// bookFlight(AirportCode.of("PAR"), AirportCode.of("CDG"), ...)
// ❌ bookFlight(passengerId, airportCode, airportCode, ...) - erreur de compilation
//    si on tente de passer un PassengerId là où un AirportCode est attendu
```

Chaque type garantit sa propre validité à la construction - les erreurs d'inversion deviennent des erreurs de compilation.
